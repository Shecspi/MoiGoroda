## Context

См. мотивацию в `proposal.md`. Модальное окно доступно из базового шаблона и
после успешного создания посещения публикует браузерные события. Сейчас
`/city/all/list` отдельно запрашивает свой фрагмент и заменяет результаты со
статистикой. Остальные list-поверхности рендерят связанные с посещениями данные
только при первоначальном запросе страницы.

## Goals / Non-Goals

**Goals:**

- Использовать единый клиентский контракт для обновления всех поддерживаемых
  list-поверхностей.
- Делегировать пересчёт фильтров, сортировки, пагинации, пустых состояний и
  агрегированной статистики серверному рендерингу.
- Заменять атомарно только область страницы, зависящую от посещений.

**Non-Goals:**

- Не обновлять карты, страницу города или публичный каталог персональных
  коллекций: для них действует отдельная логика или отсутствуют данные текущего
  пользователя о посещениях.
- Не менять API создания и редактирования посещений, модель данных либо
  сохранённые параметры фильтров.
- Не вводить клиентское состояние списков и локальные расчёты прогресса.

## Decisions

### Декларативная обновляемая область на каждой list-поверхности

Каждая поддерживаемая страница будет содержать один корневой контейнер с
устойчивым идентификатором/атрибутом и URL её fragment endpoint. В контейнер
войдут toolbar statistics, результаты или пустое состояние, пагинация, а также
timeline и фильтры, если их серверное состояние зависит от посещений.

Это исключает частичные рассинхронизации, например замену числа посещённых без
перерисовки отключённой кнопки фильтра или хронологии. Альтернатива, обновлять
отдельные карточки и счётчики из event payload, отклонена: она дублирует на
клиенте серверную логику фильтрации, сортировки, пагинации и membership
коллекций.

### Отдельный fragment endpoint для каждого существующего list view

Каждая поддерживаемая view получит маршрут фрагмента и самостоятельный шаблон,
переиспользующий include-шаблоны полной страницы. Клиент добавляет к URL
фрагмента текущую query string, сохраняя `filter`, `sort`, `country`, `page` и
специфичные параметры поверхности.

Новые или изменяемые API-endpoints для фрагментов MUST реализовываться через
`django-modern-rest` и не должны вводить зависимости от `django-rest-framework`.
Это сохраняет единый используемый в проекте API-слой и не расширяет стек
фреймворков.

Такой подход сохраняет существующую модель рендеринга и авторизации, а также
не требует определять тип страницы по URL в браузере. Вариант запрашивать
полную текущую страницу и извлекать из неё DOM отклонён: он передаёт лишнюю
разметку и может повторно создавать модалки, рекламу либо UI-скрипты.

### Единый обработчик успешного создания посещения

Общий entrypoint для list refresh будет слушать событие успешного добавления
посещения, отменять стандартное уведомление модального окна и показывать одно
подтверждение после запуска обновления. Обработчик действует только при наличии
декларативной обновляемой области, поэтому на картах и других страницах не
создаёт сетевых запросов.

Обработчик обновляет список при каждом успешном создании, включая повторное
посещение. Это необходимо, так как меняются число посещений, дата последнего
визита и сортировка, даже если уникальный прогресс не изменился. Отдельные
обработчики карт и истории города сохраняются.

### Безопасная замена и отказоустойчивость

Ответ фрагмента сначала будет разобран вне текущего DOM и проверен на наличие
полной обновляемой области. Только затем текущий контейнер заменяется целиком.
При HTTP-ошибке, ошибке разбора или неполной области клиент оставляет текущий
DOM нетронутым и выводит предупреждение с предложением обновить страницу.

## Risks / Trade-offs

- [Фрагмент забывает необходимый блок] → Контейнер заменяется только после
  проверки единого корневого элемента; integration-тесты фиксируют состав
  каждого fragment response.
- [Замена DOM снимает обработчики интерактивных элементов] → В обновляемую
  область включается только серверно-зависимое содержимое; её скрипты используют
  делегирование либо получают явную повторную инициализацию после замены.
- [Параметры URL теряются] → Общий обработчик всегда переносит текущую query
  string в fragment request.
- [Повторные уведомления] → List-обработчик централизованно отменяет стандартное
  уведомление только на страницах с refresh-контейнером.
- [Дополнительный запрос после сохранения] → Один запрос ограничен активной
  list-поверхностью и предотвращает более сложную клиентскую репликацию
  серверного состояния.
- [Смешение REST-фреймворков] → Все новые или изменённые fragment endpoints
  реализуются через `django-modern-rest`; `django-rest-framework` не добавляется.

## Migration Plan

1. Добавить fragment rendering и декларативные контейнеры, не меняя полные
   маршруты страниц.
2. Включить общий клиентский обработчик на всех поддерживаемых list-поверхностях
   и удалить частную реализацию для списка всех городов.
3. Проверить сценарии создания нового и повторного посещения с фильтрами,
   пагинацией, пустыми состояниями и ошибками фрагмента.
4. При регрессии удалить/отключить listener: полные страницы и существующие
   серверные routes остаются работоспособными; пользователь может обновить
   страницу вручную.
