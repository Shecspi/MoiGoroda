## Context

Общий Web Component добавления города публикует событие успешного создания, а
карты и детальная страница уже синхронизируют своё состояние по событиям
компонента. Список посещённых городов строится на сервере с учётом страны,
фильтра, сортировки и пагинации; его результаты и статистика должны обновляться
одинаково. См. мотивацию в `proposal.md` и наблюдаемое поведение в
`specs/city-list-refresh/spec.md`.

## Goals / Non-Goals

**Goals:**
- Обновить результаты и статистику списка как согласованное server-derived
  состояние после добавления города.
- Сохранить текущий URL и все его параметры.
- Не допустить частичной замены интерфейса при ошибочном ответе.

**Non-Goals:**
- Не заменять legacy-страницы создания и редактирования города.
- Не менять API добавления посещённого города или контракт событий для карт и
  детальной страницы.
- Не добавлять клиентскую реализацию фильтрации, сортировки и пагинации.

## Decisions

### Отдельный HTML-фрагмент использует тот же путь построения контекста

Добавляется защищённый endpoint, который повторно использует запрос и контекст
обычного списка, но рендерит только заменяемые результаты и статистику. Клиент
передаёт в него полную текущую query string.

Это гарантирует идентичность фильтрации, сортировки, пагинации и вычисленных
счётчиков полной странице. Альтернатива, вручную обновлять карточки и счётчики
из ответа API добавления, отклонена: она не покрывает все правила сортировки,
фильтрации, пагинации и морфологию статистики.

### Фрагмент имеет два явных заменяемых корня

Фрагмент содержит результаты списка и блок статистики с устойчивыми
идентификаторами/селекторами. Перед заменой клиент проверяет наличие обоих
блоков в новом ответе и текущей странице, затем заменяет оба блока.

Альтернатива, заменять каждый блок по мере обнаружения, отклонена: неполный
ответ может оставить интерфейс в несогласованном состоянии.

### Страница списка принимает ответственность за подтверждение добавления

При получении `city-added` entrypoint списка предотвращает fallback-уведомление
компонента, показывает уведомление сам и запускает синхронизацию. Другие
поверхности продолжают получать событие без изменения своего поведения.

Альтернатива, всегда показывать уведомление в компоненте, отклонена: список не
может контролировать единый порядок обратной связи для добавления и
синхронизации.

### Каждый включаемый шаблон загружает собственные template tags

Вынесенный шаблон статистики явно загружает библиотеку Django, содержащую
используемые фильтры. Вложенный include не полагается на библиотеки, загруженные
родительским шаблоном.

Альтернатива, загрузить библиотеку только в полном шаблоне списка, отклонена:
самостоятельный ответ фрагмента рендерит статистику вне этого контекста и
вызывает `TemplateSyntaxError`.

## Risks / Trade-offs

- [Повторный серверный запрос после добавления] → Запрашивать только два
  небольших визуальных блока и переиспользовать существующую query-логику
  списка.
- [Сетевой сбой после уже успешного добавления] → Сохранить прежний DOM и
  показать пользователю необходимость ручного обновления; данные на сервере не
  откатываются.
- [Одновременные добавления] → Каждый успешный ответ инициирует повторную
  синхронизацию; последняя полученная версия фрагмента является отображаемым
  состоянием. При появлении практической проблемы можно добавить сериализацию
  запросов без изменения поведенческой спецификации.

## Migration Plan

1. Развернуть endpoint и самостоятельные шаблоны фрагмента вместе с клиентским
   обработчиком.
2. Проверить добавление города при разных параметрах списка и отказе запроса
   фрагмента.
3. Откат состоит в удалении клиентского обработчика и endpoint; схема данных и
   API добавления не меняются.
